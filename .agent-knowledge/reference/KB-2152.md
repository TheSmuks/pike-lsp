# KB-2152: Optimize isStdlibModule parallel calls with batching

## Summary

`IncludeResolver.isStdlibModule()` previously spawned unlimited concurrent `bridge.resolveStdlib()` calls via `Promise.all()`, with no caching. For large workspaces, this could overwhelm the single-threaded bridge subprocess. Added an LRU cache (`MAX_STDLIB_CACHE_SIZE=200`) for stdlib check results and an inline semaphore (`MAX_CONCURRENT_STDLIB_REQUESTS=5`) to limit concurrent bridge requests. The semaphore uses the same handoff pattern as `processBatch`.

## Key Files Changed

- `packages/pike-lsp-server/src/services/include-resolver.ts`: Added `stdlibCache` (LRUCache), `stdlibSemaphore` (inline semaphore), `acquireStdlibSlot()`/`releaseStdlibSlot()` methods; modified `isStdlibModule()` to check cache then acquire slot before calling bridge; updated `clear()` to also clear stdlib cache; expanded `getStats()` return type with stdlib cache stats.
- `packages/pike-lsp-server/src/constants/index.ts`: Added `MAX_CONCURRENT_STDLIB_REQUESTS=5` and `MAX_STDLIB_CACHE_SIZE=200`.
- `packages/pike-lsp-server/src/scenarios/stdlib-queue-cache.test.ts`: New test file with 6 tests covering concurrency limiting, cache hit, cache eviction, error handling, cache clear, and stats tracking.
- `packages/pike-lsp-server/src/scenarios/include-resolver.test.ts`: Updated `deepStrictEqual` assertions to include new stdlib cache fields in `getStats()` return shape.
